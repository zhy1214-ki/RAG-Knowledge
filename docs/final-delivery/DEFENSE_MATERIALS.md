## 1. 项目介绍口述稿

本项目是“知序”知识库问答系统，重点是让用户在自己的文档中查找答案，并看到回答依据。
我使用Vue 3和FastAPI实现前后端分离，用PostgreSQL保存用户、文档片段与历史，
用Milvus Lite管理1024维向量。文件经解析和分块后进入检索流程，
回答中的来源由服务器映射到真实片段，而不是让模型自由填写文件名。
系统既有可离线演示的Mock模式，也有经过受控真实验收的Qwen和Embedding链路。
当前8080使用新版UI和Mock模式，真实模型证据来自历史单文单问验收。
我会分别说明实现、验证范围以及尚未解决的限制，不把界面演示等同于全面模型质量评估。

正式使用前请按本人实际开发经历调整人称和分工表述，不虚构团队成员、工作量或个人成果。

## 3. 技术选型说明

- Vue/TypeScript/Element Plus：承担已实现的六页面表单、列表、聊天及状态反馈；
  不宣称选型自动带来更高吞吐或安全保证。
- FastAPI/Pydantic：声明20个端点与输入/输出契约，集中处理错误。
- SQLAlchemy/PostgreSQL：承载外键、唯一约束、消息事务和来源快照；
  SQLite只是本地便利模式。
- Milvus Lite：本地持久化、COSINE与知识库过滤，适合当前单worker演示边界。
- LlamaIndex：实际只用SentenceSplitter；没有使用默认OpenAI或其完整查询引擎。
- Qwen适配：直接兼容HTTP；Mock和真实模式分别报告，不静默降级。

## 4. 核心难点与可证明的处理

| 难点 | 当前处理 | 必须承认的限制 |
|---|---|---|
| 文档与索引生命周期 | processing/indexed/failed/deleting；失败补偿；检索复核 | 外部存储无分布式原子事务，补偿可能失败 |
| 来源可靠性 | 本轮编号→模型选择→服务端来源映射→JSON快照 | 结构合法不保证每句语义正确 |
| 用户隔离 | JWT身份、owned_*、Milvus过滤及SQL JOIN | 无组织权限/RBAC；未做全面渗透测试 |
| Milvus持久化 | load_collection与release_server；真实重开回归 | 固定版本目录式存储，不能任意多进程共享 |
| UI请求重复 | busy/uncertain；超时只读查记录；不自动POST | 不具备跨标签页或全局幂等 |
| 验收资源保护 | 独立schema/存储/容器，计数/哈希/预算，失败停止 | 这些是验收设施，不是用户计费后台 |
| 安全部署 | 前端镜像备份、独立标签、只替换frontend | 未做实际回滚或远程灾备演练 |

这些是项目工程难点与实现选择，不包装为未经研究证明的算法创新。

## 6. 可能问题与参考回答

**为什么不是直接让模型回答？**  
本系统需要限定当前用户的知识库，并展示原文依据，所以先检索再构造上下文。
这不保证事实必然正确，使用者仍需查看来源。

**是不是完整使用了LlamaIndex框架？**  
项目确实使用它的SentenceSplitter，检索、存储和HTTP模型边界由自有小型适配层实现。
没有用到的框架能力不应算作本系统功能。

**如何防止编造引用？**  
模型只返回本次source_ids，服务器检查编号并映射已有片段，不采纳模型自填文件信息。
这解决结构越界，不等于证明回答每句话都得到原文支持。

**为什么Word不显示页码？**  
当前python-docx提取正文/表格，没有稳定打印页码，显示section而不伪造页数。

**删除文档后为什么历史仍能看到原文？**  
消息保存来源JSON快照。单文档删除清索引和元数据，历史保留；
删除会话/知识库会清除相关消息，需要按实际数据保留规则使用。

**能否提高worker数？**  
现实现依赖进程锁和Milvus Lite本地存储，不能直接增加worker并承诺安全。
集群化属于后续重设计范围。

**当前演示是否在调用真实Qwen？**  
不是。当前Mock；真实能力用历史M5等证据说明，不为答辩重新调用付费接口。

**系统准确率和响应速度是多少？**  
只有单样本链路和历史工具耗时，未做质量/性能统计，不提供未经验证的准确率或P95。

**是否完成生产部署和灾备？**  
完成本机新版前端部署及备份校验，未完成远程HTTPS、完整数据灾备或实际回滚演练。
